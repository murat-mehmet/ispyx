# Unlocking Windows from ispyx: design brief (Credential Provider)

Status: built and validated end to end (2026-10-27) on a real Windows 11 (build 26200) machine, local account with a password. Confirmed live through the real production path, repeatedly, across consecutive lock/unlock cycles: `src/platform/win32/unlock.js`'s `enable({password})` → elevated `install.ps1` (UAC) → DPAPI secret + release DLL registered → `isEnabled()` correctly reports true → `signal()` → Win+L → unlocked automatically, no interaction, no polling (the watcher thread blocks on `FindFirstChangeNotificationW`, see below). Unit tests (`npm test`, `npm run panel-test`, `npm run auth-panel-test`) all pass with the new panel/resident/server code. **Not yet exercised**: clicking the actual browser panel toggle (the underlying `setUnlock` action is the same code path already proven via the manual test script, so this is thin UI wiring, not a new risk) and calling the `unlock` MCP tool through a real MCP client. Packaging (shipping the compiled DLL inside the npm package, since end users have no Rust toolchain) is not done. Mirrors `docs/unlock-mac.md` for the other platform.

## The ask

The user stores their Windows account password (or PIN) once, in the panel, deliberately and knowingly. When the machine is locked, an AI using ispyx can ask it to unlock the session so it can keep working unattended. The user accepts the trade-off: whoever can reach the ispyx server while the PC is locked can unlock it.

## Why a Credential Provider, not a synthetic-key approach

The lock screen (`LogonUI.exe`) runs on the secure desktop; a normal process cannot post keystrokes into it, and trying to defeat that boundary with privilege tricks is the approach we're explicitly avoiding here. A **Credential Provider** is Microsoft's own, documented extension point for adding a login/unlock method to that same screen — it runs *as part of* LogonUI, in-process, with no desktop-boundary trick needed. This is how Windows Hello, smart-card logon, and third-party SSO/MFA agents show up as tiles on the lock screen.

Docs: `ICredentialProvider`/`ICredentialProviderCredential` (COM interfaces), registered under `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Authentication\Credential Providers`. Each provider is a COM DLL with a CLSID, loaded by LogonUI when the lock/logon screen appears.

## Shape of the solution

1. **A small native COM DLL** (C++ or Rust; Node cannot register as an in-proc COM server for this) implementing `ICredentialProvider`. It offers one tile: "Unlock with ispyx". Selecting it does not ask the user anything — it reads a stored, encrypted secret and calls `SetSerialization` with the user's actual Windows credential, exactly as a smart-card provider would after reading the card.
2. **Where the secret lives:** DPAPI-protected (`CryptProtectData`, machine-scope, SYSTEM-only, since LogonUI runs as SYSTEM before the user's DPAPI user keys are available). Written once when the user turns the feature on in the panel (elevation prompt at that moment, not at every unlock). Never passed to or readable by the AI.
3. **How ispyx triggers it:** the credential provider DLL also exposes a tiny local signal (e.g. watches a named event or a file it alone can read) that the *running* resident sets when the `unlock` tool is called and the screen is locked. On seeing the signal, the already-loaded provider auto-submits its tile instead of waiting for a click. This avoids needing ispyx itself to run with SYSTEM rights at unlock time — only the DLL, which LogonUI itself loads as SYSTEM, touches the secret.
4. **Install:** ships as part of the normal Windows install/update (`scripts/install.ps1`), with one elevation prompt to register the DLL and (re)write the DPAPI secret whenever the panel toggle or stored password changes. No scheduled task, no second long-running elevated process.
5. **Panel UI:** a switch, "Let the AI unlock this PC", off by default, with the password field and a one-line explanation of the trade-off; turning it off re-registers the provider with the secret cleared (or unregisters it).
6. **ispyx side:** a `unlock` tool, no parameters, works only while the screen is locked; it does not touch the secret directly, only signals the provider and then polls `isScreenLocked()` the way the Mac doc does, with a timeout and a plain error if it doesn't clear.

## Confirmed by the spike (2026-10-26)

- `GetSerialization` with a plain `KERB_INTERACTIVE_LOGON`/`KERB_INTERACTIVE_UNLOCK_LOGON` blob (packed the way Microsoft's own Credential Provider sample packs it — offsets, not real pointers, since the buffer crosses into LSA's address space) **does** complete the unlock, same as typing the password. Confirmed instant — no perceptible latency.
- This Windows 11 build (26200) sends third-party providers `CPUS_LOGON`, not `CPUS_UNLOCK_WORKSTATION`, even for a plain single-user lock screen. `SetUsageScenario` must accept both; gating on `CPUS_UNLOCK_WORKSTATION` alone means the provider never gets asked.
- A local account's logon requires `LogonDomainName` set to the machine's own NetBIOS name (`GetComputerNameW`), not blank. An empty domain produces `STATUS_LOGON_FAILURE` (`0xC000006D`) even with the correct password — this cost real debugging time before being traced to the domain field.
- **Security requirement, not optional:** the tile must not exist at all unless a fresh, short-lived external signal is present (the spike uses a file's mtime, <20s old). Without this, the tile is a standing full-auth bypass for anyone physically at the machine, not just ispyx — confirmed as a real gap before the gating was added.
- **Safety requirement, not optional:** the signal must be single-use — consumed (deleted) the moment `GetSerialization` is invoked, success or failure, before the result is known. Without this, an unconditional `SetSelected` → autologon=`TRUE` caused a real incident: a wrong/stale credential made LogonUI auto-resubmit on every reselection, looping on "incorrect password" until a hard restart, with the user never having clicked anything. With single-use consumption, a failed attempt tries exactly once, the tile disappears, and the user's own manual sign-in is immediately unaffected. Verified both outcomes live: correct password → one attempt, `status=0x0`, unlocked; wrong password → one attempt, `status=0xC000006D`, tile gone, no retry.
- **DPAPI storage confirmed working end to end.** The crate moved from `native/win32-unlock/spike` to `native/win32-unlock/provider` (package renamed `ispyx_unlock`, CLSID unchanged) and now reads `C:\ProgramData\ispyx\unlock.secret`: a `CryptProtectData`/`CRYPTPROTECT_LOCAL_MACHINE` blob wrapping three length-prefixed UTF-8 fields (domain, username, password). The real access control is the file's ACL (Administrators/SYSTEM only — LOCAL_MACHINE-scope DPAPI itself can be decrypted by any local account that can read the ciphertext, so the ACL is load-bearing, not DPAPI). The signal file (`C:\ProgramData\ispyx\unlock.signal`) gets a narrower ACL: Administrators/SYSTEM plus the specific resident user, granted write access at setup time — not the `Users` group, so no other account on the machine can trigger it. Confirmed live: locked, signal refreshed, unlocked instantly and silently with the correct DPAPI-stored password; a stale/wrong secret or signal behaves the same as the plaintext-file spike (one attempt, no retry). `native/win32-unlock/provider/setup.ps1` is a **dev-only** test helper (password as a command-line argument, visible in process listings) — the real installer step needs a proper masked prompt, not this script as-is.
- **regsvr32 `/s`'s exit code is not trustworthy for confirming registration.** Hit this directly: `regsvr32 /s <dll>` reported success (`$LASTEXITCODE -eq 0`) while the registry's `InprocServer32` default value was left pointing at the old (by then deleted) path — `DllRegisterServer` was silently never invoked. Running without `/s` (shows the real success/failure dialog) and/or checking the registry value afterward is the reliable way to confirm; any install/setup script must not rely on `/s`'s exit code alone.
- Unregistration/re-registration is a non-issue in practice: LogonUI loads the DLL fresh from disk on every lock cycle (confirmed via sequential lock cycles with different PIDs each time), so a rebuilt DLL takes effect on the next lock without re-running `regsvr32` — only the registry pointing at the right path matters, not re-registering after every rebuild.
- **The realistic case — screen already locked, signal arrives later — needed a fix, and now works.** `GetCredentialCount` is only queried once, when LogonUI loads the provider at lock time; it is never polled again on its own (confirmed: a provider sat loaded for 30+ seconds with no re-query). A signal that becomes fresh *after* the lock screen is already up was invisible until the provider actively calls back. Fix: `Provider::Advise` now stores the `ICredentialProviderEvents` it's handed and spawns a worker thread that polls the signal every ~300ms; the instant it flips stale→fresh, the thread calls `events.CredentialsChanged(upAdviseContext)`, which makes LogonUI immediately re-query `GetCredentialCount` and proceed. Confirmed live: locked first with no fresh signal, waited, then the signal was set ~17s into the lock — the provider noticed, LogonUI re-queried, and it unlocked with no visible tile and no interaction at all (since `bAutoLogonWithDefault=TRUE` skips showing the tile when the count is fresh — unlocking is instant and silent, which is the right behavior for the real feature). This is the mechanism the real ispyx-resident-to-provider signal needs to replicate (a named event or equivalent working the same way), not just the file-mtime check alone.

## Confirmed in the Node/panel wiring (2026-10-26)

- **`Start-Process -Verb RunAs` rejects `-WindowStyle` in Windows PowerShell 5.1.** The first elevation attempt from `src/platform/win32/unlock.js` failed silently before any UAC prompt because the outer script passed both `-Verb RunAs` and `-WindowStyle Hidden` to `Start-Process` -- PS 5.1 throws a parameter-binding error for that combination. Fixed by dropping `-WindowStyle` entirely.
- **An elevated child's stdout/stderr never reaches the caller.** `Start-Process -Verb RunAs` runs the child in its own console with no redirection back (`-RedirectStandardOutput`/`-RedirectStandardError` are themselves rejected together with `-Verb`). `install.ps1`/`uninstall.ps1` write their result (`OK` or `ERROR: ...`) to a `-ResultFile` path instead, which the caller reads back after the elevated process exits -- Write-Output alone is invisible to the Node side.
- **`fs.existsSync` cannot tell "missing" from "exists but access denied".** `isEnabled()` checks for `unlock.secret`, whose ACL (by design) denies read to the account's own normal, non-elevated token -- exactly the context the resident always runs in. `existsSync` swallows every stat error and returns `false` either way, so it reported "not enabled" immediately after a real, successful install. Fixed with `statSync` + checking `e.code !== 'ENOENT'`.
- UAC being set to "never notify" (confirmed on the test machine) does not skip the elevation mechanism itself, only the consent prompt -- `Start-Process -Verb RunAs` still elevates correctly and `install.ps1` still needs the account to actually be an administrator.

## Tried and reverted: a named Win32 event instead of the signal file

To remove the watcher thread's 300ms poll loop, the signal was switched from a file's mtime to a named, ACL'd, manual-reset Win32 event (`ispyx-unlock-signal`) that the resident would `Set()` and the DLL would block on via `WaitForMultipleObjects`. This failed in practice and was reverted:

- **A named kernel object only exists while some process holds a handle open.** `install.ps1` created the event, then its own process exited (closing its handle), and the OS discarded the object immediately -- a later `OpenExisting` from the resident failed with "No handle of the given name exists." Confirmed directly: the event was gone within moments of the elevated script finishing, long before any `signal()` call.
- Nothing in this architecture is positioned to hold a handle open continuously between an `enable()` and a much later `signal()` (which could be hours or days afterward): the DLL only exists transiently, per lock cycle, and the resident has no long-lived native handle of its own without adding a second background process or a native Node addon -- both of which the brief rules out.

## A second bug from the same root cause, found after reverting to the file

`consume_signal()` originally deleted `unlock.signal` after each attempt (the one-shot safety mechanism). This broke the *first* time it ran for real: the file's ACL (set once at install time) grants the resident's account write access to that one file, not *create* rights on the `C:\ProgramData\ispyx` folder itself (locked to SYSTEM/Administrators at install time). Deleting the file meant the next `signal()` had to create a brand new file in a folder the account has no rights in -- confirmed directly, it failed with `EPERM`, and the feature could only ever be used once per install. Fixed by having `consume_signal()` age the file's mtime to the Windows epoch (`SetFileTime`) instead of deleting it: the file now persists for the life of the install, so every future `signal()` is a plain write to an existing file, which the one-time ACL grant already covers forever. Confirmed live across several consecutive lock/signal/unlock cycles after the fix.
- **The fix that keeps the "no polling" goal without this problem:** stay with the file (it needs no open handle to persist), but replace the watcher thread's sleep-poll with `FindFirstChangeNotificationW` on `C:\ProgramData\ispyx`, which blocks with no CPU use until something in the directory changes. `is_signal_fresh()` (the file-mtime check) stays the authoritative check on each wake, since a wake can be spurious (the DLL's own `unlock.log` lives in the same directory) -- the existing `was_fresh` edge-transition check still gates when to actually notify `CredentialsChanged`, so a burst of incidental wakes still only notifies once per real signal.

## Distribution

End users have no Rust toolchain, so the release-built DLL is committed at `native/win32-unlock/bin/ispyx_unlock.dll` and shipped in the npm package (`files` in package.json, along with `install.ps1`/`uninstall.ps1`). Rebuild it with `cargo build --release --target x86_64-pc-windows-gnu` in `native/win32-unlock/provider` and copy the result over. `install.ps1` copies the DLL into `C:\ProgramData\ispyx` (admin-only ACL) and registers that copy: LogonUI loads it as SYSTEM, so registering the user-writable npm directory would let any local user get code running as SYSTEM.

Verified through a real MCP client (stdio `ispyx mcp` against an isolated dev resident): `unlock` is listed and returns `alreadyUnlocked` on an unlocked desktop. The panel toggle's click path (UAC prompt, password entry) still needs a hand run.

## Known gaps — out of scope for now

Researched and deliberately not pursued (see rationale per item):

- **PIN sign-in / Microsoft Account (MSA).** A PIN is not a replayable secret — it unlocks a TPM-bound NGC (Windows Hello) key, and the real LSA auth is a challenge-response using that key, not a password submission. No documented API lets a privileged local component complete that challenge-response given just the PIN value; the WinRT surfaces that touch it (`KeyCredentialManager`, `UserConsentVerifier`) require a live human gesture by design. Workaround considered and **rejected**: forcibly setting/overwriting the account's local password via `NetUserSetInfo`/`net user` so our existing mechanism has something to submit — for an MSA-linked account the local SAM password entry is a synced cached verifier tied to the real online password, and overwriting it desyncs the cache from the real credential and can break the user's normal sign-in until they reconnect/reverify online. It also does **not** change the real online Microsoft password (that's server-side) — it just corrupts the local copy's relationship to it.
- **Driver-level keystroke injection as an alternative for PIN accounts.** Idea: instead of replaying a secret, automate *typing* the PIN into the real Windows Hello PIN tile via a kernel-mode virtual HID (keyboard) driver — input from an actual HID device stack reaches the secure desktop (user-mode `SendInput`/`PostMessage` does not; that's the boundary that forced the Credential Provider approach in the first place). This is reportedly how remote-access tools interact with the physical lock screen. Technically real, but disproportionate for this project: no turnkey signed virtual-HID keyboard/mouse driver exists (`ViGEmBus` is gamepad-only and frozen; `HidGuardian`/`Interception` are unmaintained filter drivers), and a Windows 11 kernel driver now needs Microsoft Partner Center attestation signing with an EV code-signing certificate — realistically weeks to months of dedicated kernel/HID work plus ongoing signing overhead, a separate product rather than a feature increment.
- **Genuinely passwordless accounts** (no password and no PIN — biometric-only, or no credential object at all). No software-only path exists by design: biometric auth requires a live physical sensor read that can't be replayed in software. The one API that looked promising, Companion Device Framework, is both access-restricted (needs Microsoft's special onboarding) and deprecated since Windows 10 2004.

**Practical mitigation:** the panel must classify the account before enabling the feature and refuse/warn rather than silently fail — local account with a real password → supported; MSA-linked sign-in → refuse with an explanation. **Does not** try to predict "no password set" up front: the only signal Windows exposes for that, `UserFlags`' `UF_PASSWD_NOTREQD` bit (`net user`'s "Password required"), means the password-policy check is waived for the account, not that the password is blank -- confirmed a false positive against this session's own test account, which has a real, working password. A wrong/blank stored secret is already caught safely at unlock time instead (one attempt, no retry).

## Suggested test setup

The spike was tested directly on the primary dev machine (not a disposable VM), deliberately — its `C:` volume runs UWF (Unified Write Filter, "Protected" state), so any bad state reverts on reboot. This is a reasonable substitute for a throwaway VM *only* when UWF (or an equivalent revertible setup) is confirmed active beforehand. Without that safety net, use a disposable VM with a throwaway local account instead — a bug in an early credential provider can make an account temporarily unable to log in normally (removable by booting to safe mode / another admin account and deleting the registry key, but annoying). Keep a second admin account or snapshot you can roll back to before testing either way.
